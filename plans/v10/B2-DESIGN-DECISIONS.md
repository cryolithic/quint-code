# B2: решения после ревью, 24 сентября 2026

**Выбрано для реализации в тикетах; в коде ещё не реализовано.** Иван прямо
поручил выбрать подходящие решения и обновить план; изменения кода он поручил
включить в тикеты. Эта запись не запускает B2, не выпускает API и не меняет
исторические ответы в [DECISIONS-LOG](DECISIONS-LOG.md).

Предмет — существующий Haft и способ работы инженера с ним через coding agent.
Нужный результат — проверяемая спецификация, понятные основания и продолжение
работы без собственного framework для сбора evidence. Выбор действует для B2A;
пересмотр — после его измерений либо изменения источников/условий ниже.

Правило выбора объявлено до реализации: сохранить точную основу и данные;
уменьшить необходимую работу инженера и агента; предпочесть небольшой обратимый
шаг поверх общего ядра. Число tools, schemas, строк и токенов — отдельные
наблюдения, не универсальная функция ценности. Пользу всей системы эти решения
пока не доказывают.

## D1. Пять инструментов по задачам, один application core

Сравнены: оставить один широкий `haft`; вернуть буквально старые пять
`remember/recall/context/impact/fpf`; выделить пять пользовательских задач.
Выбран третий вариант:

| Tool, планируемое имя | Граница |
|---|---|
| `haft_read` | Поиск/точное чтение, context, impact, части и продолжение чтения |
| `haft_write` | Запись носителя, terms и сохранение captured evidence по refs |
| `haft_change` | Подготовка, preview, apply, rebase, archive и явное recovery |
| `haft_check` | Структурная проверка, prepare, ограниченный capture и observe |
| `haft_fpf` | Status/search/inspect закреплённого FPF/DPF источника |

Это тонкие адаптеры к одному core, без пяти сервисов и дублирования merge.
Схемы закрыты по action: обязательные параметры и допустимые сочетания видны
до вызова. Один каталог операций порождает schema/help/описания/skill-примеры;
server instructions и ответы достаточны без skills. Для hosts с ограниченным
JSON Schema renderer должен сохранять понятные описания, а server-side validation
всегда сохраняет те же инварианты. Host-specific tool search не требуется.

Чтение не маскируется общим destructive tool. Аннотации соответствуют самому
сильному возможному эффекту каждого tool; это подсказки host, не разрешения.
Запуск project tests в `haft_check` — явный эффект. Source fetch/pin mutation
не прячется в read-only `haft_fpf`: будущий T08 задаёт отдельную CLI-операцию.

B1 `haft.api/2` CLI сохраняется. Для старых MCP consumers предоставляется явно
выбранный compatibility profile с прежним единственным `haft`; одновременно
оба каталога по умолчанию не показываются. Advertised next requests всегда
исполняются в выбранном profile; сохранённые receipts и payload digests не
пересчитываются. B1 читается по [фактическому каталогу](INTERFACE-BASELINE.md).

Основание: ясные задачи и типизированные входы рекомендует
[OpenAI](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions);
у [MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
схемы и annotations относятся к отдельному tool. Ни один источник не доказывает
оптимальность именно пяти. Слабое место — перенос сложности внутрь actions;
проверка — ошибки выбора/аргументов и время до полезного ответа в T03.
Если выигрыш отсутствует, вернуть compatibility profile как default без отката данных.
Реализация: **T01A**.

## D2. Спецификация — содержание и редакции; принятие решения отдельно

Сравнены: оставить `proposed/active + operator_confirmed` для spec; убрать всю
информацию о происхождении и принятии; отделить spec content от decision binding.
Выбран третий вариант. Новый авторский формат `haft/2` сохраняет claim IDs,
L/A/D/E различения, условия, примеры, `implemented_by`, `checks` и точные editions.
У spec нет authoring status и `operator_confirmed`; её текущая редакция определяется
явным change/CAS, а не вторым lifecycle. Происхождение правки остаётся.

Текущий текст спеки не доказывает реализацию, успешность проверки, человеческое
принятие продуктового выбора или разрешение выпуска. Агент редактирует его в
рамках порученной работы; изменения binding decision по-прежнему требуют точного
запроса человека. Для decision сохраняются `proposed/active`, честные origin и
`operator_confirmed` по выбору №2. Git review остаётся обычным способом приёмки
кода/спек, но наличие commit само по себе не становится полномочием.

Версия меняется явно: B1 `haft/1` и его snapshot/interpretation продолжают
читаться со старым смыслом. Существующий proposed spec не превращается молча
в current v2. Адресная операция переавторства показывает diff, сохраняет старый
носитель/снимок и происхождение; несовместимый reader получает unsupported.
В B2A никаких массовых переписываний базы. В новом формате status разрешён
только там, где имеет определённую семантику; неизвестные extensions сохраняются.

Слабое место — пользователь может принять current spec за согласованную политику.
Приёмка требует отдельно показать current content, decision authority, implementation
и evidence, включая отказ при противоречащем binding decision. Реализация: **T01B**.

## D3. Автоматизировать механический сбор, сохранить основания

Выбран встроенный ограниченный capture adapter вместо одноразовых Python helpers
и вместо собственного agent runner. Он исполняет ровно объявленную project test
command с фиксированными cwd/env/selector, лимитами и timeout; собирает actual
exit/stdout/stderr и основу, использует существующие prepare/observe/retain.
Импорт результата внешнего runner остаётся. API не выдумывает oracle, failure
matcher или подтверждение оператора. Нет daemon, nested agent, scheduler.

Выдаваемый server-side ref позволяет сохранить bytes без base64 roundtrip через
контекст модели. Большой результат остаётся читаемым по частям. По умолчанию
summary отвечает на вопрос о claim/check; полный payload скачивается только
для нужного receiving use. Доступ к каждой части остаётся проверяемым.

Дорогой результат не оправдывает ослабление смысла `pass`. Ошибка matcher,
неисполненный selector, zero tests и environment failure остаются различимы.
Слабое место — удобный capture может расширить эффект; команда и область должны
быть явными, test-owned fixtures обязательны. Реализация: **T01**.

## D4. Упростить хранение без удаления доказательства

Markdown остаётся авторским источником. Точные content-addressed снимки и
журнал восстановления нужны для исторических refs и multi-file publish;
Git history сам по себе их не заменяет. JSON/base64 — текущий B1 encoding,
не требование показывать его модели или человеку.

Первый шаг — измерить физические классы данных и удалить лишнее копирование:
повторные одинаковые outputs/preimages ссылаются на один проверенный blob,
runtime scratch и build cache не становятся переносимыми evidence по умолчанию.
Ограничение capture не делает частичную основу полной. Необходимые dependency/oracle
bytes, unknown extensions и старые digests сохраняются; если выбранный scope
неполон, результат показывает точный предел. Для смены durable encoding нужен
новый формат с reader старых снимков; существующие hash-addressed bytes не менять.

Не вводим SQLite без измеренной потребности: B1 использует файловый store и JSON
disclosure cache; SQLite сейчас нужен только для чтения v9 при миграции.
Не сокращаем result kinds механически: агент видит понятный краткий исход,
диагностика сохраняет причины. Не строим TypeEnv: interpretation — версия
локального parser + нужные terms; обязательность каждого пользовательского поля
должна иметь конкретный неоднозначный случай. Ненужные defaults задаёт core,
а не агент при каждом вызове.

Слабое место — дедупликация может усложнить перенос. Приоритет у автономного
clone/recovery; уменьшение bytes не принимается ценой недоступной истории.
Реализация: **T01C**; введение нового durable format — только если измерение
покажет повторное хранение значимых bytes, а не только большой Go cache.

## D5. B2A сейчас, B2B остаётся в очереди

Варианты: сразу наращивать полную parity; остановить v10 до идеального benchmark;
исправить известные затраты и затем решить, какое расширение оправдано.
Выбран третий. B2A — T00, T01A, T01, T01B, T01C, T02, T03A, T03.
B2B — T04–T10: workflow/config, batch, shared roots, source sync и общая
спецификация для двух компонентов. Цель OpenSpec parity не отменена, но её
исполнение не активируется одним техническим pass.

Техническая пригодность, доступность испытания и сравнительная польза — три
отдельных результата. Отсутствие native MCP/auth — `blocked_external` для
конкретного наблюдения. Корректные данные без различимого выигрыша —
`inconclusive`, не failure и не continue. Исправимый дефект — `revise`.
Протокол сравнения находится в [B2-EVALUATION](B2-EVALUATION.md).

T00 проверяет cloud capability в начале. Core/CLI и fixtures можно реализовать
в обычном облачном контейнере. Native sessions могут исполняться в квалифицированном
headless host на удалённой машине; laptop не требуется. Протокольный клиент
не заменяет агента. Новые платные ресурсы/ключи не считаются уже предоставленными.
При недоступности native host T03A может закрыть техническую часть B2A, а T03
остаётся явно незавершённым. Перекрывать этим независимые исправления нельзя.

Слабое место — отложенная продуктовая обратная связь. Поэтому T00 обязан рано
назвать доступный путь испытания или точный внешний input, а не обнаружить его
отсутствие в конце. Полное B2 не закрывается до B2B и его qualification.

## D6. Переносимые основания и ограничение документации

Публикуются безопасная производная копия сравнения, таблица цены и определения
R1–R10. Локальные raw host traces остаются неопубликованными; manifest различает
опубликованные агрегаты и отсутствующие исходники. SHA истории не повышается
до нового source SHA. Общие правила тикетов находятся в одном README.

Текущие контракты редактируются в `plans/v10`. Docs submodule остаётся pinned
published B1 snapshot; его feature branch не считается merged release. T10/B4
должны подготовить отдельную публикацию. Два FPF pin временно нужны двум runtime:
их размер — долг B4, а не повод сломать v9 сборку в B2.

## Источники и предел рекомендации SoTA

Прямое применение FPF/DPF и поправки к Claude разобраны в
[семантической проверке](source-review/B2-REV3-2026-09-24.md).
Внешние источники проверены 24 сентября 2026, используются как инженерные
ориентиры, не как измерение Haft:

- [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents):
  ясные задачи, содержательные ответы, измерение ошибок и затрат на реальных задачах.
- [Agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents):
  повторы, изоляция попыток, проверка graders и чтение trajectories.
- [Function calling](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions):
  строгие понятные входы, снятие механической нагрузки, проверка числа tools опытом.
- [MCP tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools):
  schema, annotations и structured output; annotations не являются authority.

Числа повторов и пороги в нашем протоколе — локальная политика этой пробы.
Ни FPF, ни публикации не утверждают, что выбранная архитектура уже победила.
